# Agent Note: Oasis UI 进度只能通过按会话保存的用户确认推进

Status: implemented

[English](2026-08-16-oasis-ui-user-confirmed-progress.md) | 中文

## 问题

Oasis UI 启动器展示了预期阶段，但这些阶段只是静态标签。提交请求后弹窗关闭，却没有记录当前处于哪一步，因此重新打开或刷新后无法告诉用户接下来该做什么。如果由 Agent 推断或报告进度，对话中的完成声明就会与用户验收混在一起，并可能把计划或未验证的工作显示为已完成。

## 决策

`ui-oasis-workflow` 为每个会话维护一个浏览器本地 `OasisUiProgressStore`。该 store 按 `dsh.oasis-ui.workflow.<sessionId>` 保存文字版或桌面版模式、原始任务请求、当前阶段，以及 `ready`、`awaiting_confirmation`、`complete` 状态。只有启动器提交阶段 Prompt 时，阶段才从 `ready` 进入 `awaiting_confirmation`；只有用户点击确认命令时，阶段才会推进。修改请求保持在同一阶段；确认阶段只解锁下一阶段，绝不会自动提交下一阶段。

八个阶段定义同时为 UI 指引和模型可见 Prompt 提供唯一来源。每个定义都说明 Agent 工作、用户验收项和预期产物。每条 Prompt 都标明所选模式与准确阶段，禁止执行后续阶段，并要求 Agent 停下等待用户确认。Host 系统提示明确说明 Agent 输出不能推进启动器状态。

持久化状态记录的是交互进度，不是产物事实。UI 文案与 Prompt 把静态文件、生成位图、Workbench 状态、编辑器保存、PIE 和多人检查分别作为独立证据。剪贴板入口在分配浏览器预览前使用当前会话的 Host 图片限制，因此启动器不会绕过输入框的张数或字节检查。

## 考虑过的替代方案

- **从最近一条 Agent 回复推导进度**：不予采纳。自然语言中的完成声明不是可靠的验收记录，也无法区分计划与已经执行的验证。
- **提交每个阶段后立即推进**：不予采纳。用户会失去审核点，而且失败或未完成的 Agent 轮次也会解锁后续工作。
- **保存一份全局工作流状态**：不予采纳。多个对话可以承载彼此独立的 UI 任务，不能互相覆盖。
- **只保存阶段序号**：不予采纳。重新打开时会丢失所选交互模式和构建后续阶段 Prompt 所需的任务上下文。

## 后果

- 关闭弹窗或刷新浏览器后，会恢复当前对话的模式、任务、阶段和确认状态；其他会话保持隔离。
- 用户必须明确确认全部八个阶段。这会为每个阶段增加一次有意操作，但换来可追溯的审核点并防止自动跳步。
- 清除浏览器存储会重置启动器进度，但不会删除对话消息或项目产物。反过来，持久化进度也不能证明这些消息或产物仍然存在；需要时 Agent 必须重新发现真实文件。
- 组件测试锁定模式选择、阶段锁定、修改、完成、持久化和会话隔离；组装后的 `oasis-ui-workflow` 快照锁定模型实际看到的 Host 指令。
